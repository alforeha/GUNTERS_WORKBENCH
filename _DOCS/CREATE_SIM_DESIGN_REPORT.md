## 0. How to read this

Sections 1–7 define the **model** (feature, types, region, object, building,
utility, ground, representation, evidence). Section 8 defines the **first
Create Sim UX**. Section 9 lists the **required schema / viewer / UI changes**.
Section 10 is the **risks/unresolved** list. Section 11 is the **roadmap and
recommended next manager**. The implementation plan doc turns Section 8–9 into a
buildable v1 scope.

The one idea that governs everything below: **parametric authoring.** A feature
is not hand-modeled geometry; it is *authored parameters + evidence* from which
the system **generates** the reality geometry, the plan/CAD linework, and the
report quantities. The user draws a footprint and sets a height; the mass, roof,
faces, and plan lines fall out. The user draws a border and picks "asphalt" with
a decay value; the surface patch, material, and hatch fall out. This is the
"procedural" the owner wanted — generation from *your* parameters — as distinct
from *auto-extraction* from the cloud, which is explicitly deferred.

## 1. What is a Create Sim feature?

A **feature** is an interpreted, user-authored thing — an object, area, line,
surface, note, or measurement — that carries its own authorship, evidence, and
parallel representations. Features are the sim's content. They are **not**
assets: an asset is a stored database (immutable source or regenerable derived);
a feature is an interpretation *authored to the sim* that may draw evidence from
one or many assets.

**Feature truth is not asset truth.** An asset carries `truthStatus`
(`source | indexed-full | derived | …`) describing how measured/reliable the
*data* is. A feature carries **authorship + confidence** describing how the
*interpretation* came to be. The two never mix. A feature can be highly
confident while sitting on `preview-sampled` data, or low-confidence while
sitting on `indexed-full` data. Keeping these separate is the single most
important invariant in this design (Risk 2).

Recommended feature record (refines the handoff's starting point):

```
Feature:
  id                                       # stable unique
  simulationId                             # FK to the singleton sim
  family        region | object | building | utility | line | marker | measurement
  templateId    | null                     # catalog stamp this instance is of
  subtype       string                     # e.g. "asphalt", "tree", "gable"
  name          string
  lifecycleStatus  draft | authored | reviewed | flagged
  authorship    authored | assisted | derived | edited | imported
  confidence    low | medium | high        # authoring confidence, NOT asset truth
  evidenceRefs  EvidenceRef[]              # see Section 7
  geometry      FeatureGeometry            # authored primitive(s); see below
  parameters    Record<string, unknown>    # per-instance template params
  representations  { reality, cad, report, export }   # see Section 6
  display       { visible, colorOverride?, drawOrderHint? }
  metadata      Record<string, unknown>
  createdAt / modifiedAt
```

Two refinements over the handoff draft, both from the co-design session:

- **`family` + `templateId` + `parameters`** replace a flat `type`/`subtype`
  pair. The catalog template supplies the type and its parameter *schema*; the
  instance stores its parameter *values*. This is what lets one "tree" stamp
  produce a whole varied stand — instance A is 40 ft with a wide dripline,
  instance B is 12 ft with sparse leaf coverage — without a new type each time.
  **(owner, 2026-07-09)**
- **Authorship vocabulary (final):** `authored` (drawn/placed by the user),
  `assisted` (user confirmed a system suggestion — future), `derived`
  (generated by automation — future), `edited` (started one way, user changed
  geometry/params), `imported` (seeded from a DWG/LandXML asset). v1 writes only
  `authored`, `edited`, and `imported`.

`geometry` is the small set of **authored primitives** — never a raw mesh. A
feature stores what the user actually drew (a point, a polyline, a closed
polygon, a footprint + height) and the engine derives display geometry from it.
This keeps the manifest small and human-readable and keeps regeneration cheap.

## 2. Feature type hierarchy (what exists first)

The owner's ruling: **every family gets its own authoring toolset** (one authors
regions, one authors objects, etc.), and the specific subtype is a **dropdown
selector inside that toolset** (Add Region ▸ asphalt / concrete / grass; Add
Object ▸ vegetation / light pole / hydrant), with a generic-then-classify
fallback where a user drops a generic feature and sets its subtype in the right
panel afterward. **(owner, 2026-07-09)**

Families and their v1 depth:

| Family | v1 scope | Deferred |
| --- | --- | --- |
| **Region** | Closed/opened border + breaklines; parametric material (decay, vertical scale) | Region→ground stitching engine, vertical regions as walls |
| **Building** | Footprint polygon + height + roof type → mass, roof outline, face/overhang plan lines | Doors, windows, garages, decks, multi-plane roofs, faces as editable sub-features |
| **Object** | Place from catalog by snapping; per-instance scale params (tree height/dripline/leaf) | Detailed meshes, cloud-mass evidence auto-fit |
| **Line / breakline** | Standalone polyline + breakline draw + snap | Vertical breaklines (curbs/walls) as generated faces |
| **Marker** | Bodyless labeled point; doubles as a **control point** and a **spot-elevation** (measured Z) surface constraint | Photo/flag linking, review workflow |
| **Measurement** | Existing `measurement` feature, kept | Area/volume rollups |

Aggressive simplification for v1 is deliberate. Utilities get a *tab and catalog
seeds* but reuse the Object/Line toolsets rather than a bespoke engine (Section
5). Buildings stop at footprint + roof with an **explicit ramp** to openings and
decks (Section 4).

Recommended v1 catalog seed (short, trusted, JSON — Section 6.5):

```
Regions:   asphalt, concrete, gravel, grass, dirt, water, unknown
Objects:   tree (vegetation), light pole, sign, hydrant, manhole, generic
Buildings: flat-roof, gable, hip
Lines:     curb, flowline, ridge, ditch, edge-of-pavement, fence, generic breakline
Markers:   review flag, control point, spot elevation, generic
```

## 3. Region model

A **region** is a material/area feature — the project's replacement for the
vague word "texture." It is authored as a **border first, refined with
breaklines**, and (when ground-level) *is itself a 3D surface patch*, so
authoring a region authors surface, material, and (via export) hatch at once.

**Parametric material (the owner's model).** A region template is a *type plus a
parameter schema*, not a fixed look. Examples the owner specified:

- **asphalt / concrete** — a `decay` parameter: `0` reads smooth and uniform;
  high `decay` reads patchy/worn. Same stamp, a spectrum of looks.
- **grass** — a `verticalScale` parameter: mowed lawn = low, farm field = tall.
  This is a display height above the ground patch, not a survey measurement.
- Every region also has the shared fields: color/tint, pattern, and a
  **height behavior** (`draped` on the ground / `floating` / `vertical`).

**Answers to the required region questions:**

- *Always closed polygons?* No. Borders may be **open** (data simply ends at the
  scan edge) or **closed** (the feature actually terminates). Open borders are
  legal and common; the ground compiler treats an open edge as "unknown beyond,"
  not as a wall.
- *3D patches?* Yes — a ground-level region **is** a surface patch. Its geometry
  is the border polygon draped/fitted to evidence; breaklines shape its interior.
- *Vertical regions?* Modeled but **deferred** to a later phase. A vertical
  region (a wall face, a retaining face) is the same feature with
  `heightBehavior: vertical`; v1 does not generate vertical faces.
- *Part of ground compilation?* Yes — ground-level regions are the primary input
  to the ground surface (Section 5). Non-ground regions (roof material, water at
  a different datum) are excluded from ground stitching.
- *Interaction with TIN triangles?* A region contributes its border + breaklines
  as constraints; the ground compiler triangulates within/between regions along
  shared edges. v1 stores the constraints and renders the patch; the *stitched*
  TIN is a later surface-manager phase.
- *Does a region own hatch metadata?* It owns a **CAD representation reference**
  (layer + hatch pattern name), resolved from its template/codelist. The region
  does not store raw hatch geometry; hatch is generated at export. This prevents
  representation drift (Section 6).

**Corridor / "roadway" (deferred generator — owner idea, refined 2026-07-09).**
Best modeled not as a single region but as a **line-driven generator**: the user
authors a **centerline** (a line) plus a **left/right cross-section profile**
(offsets to edge-of-pavement, curb face, curb back, gutter…), and the corridor
**emits multiple parallel regions and their shared breaklines** — the travel
surface as one region, the concrete **curb** as its *own* region, gutter as
another — each with the correct material, each feeding the surface. So a corridor
is a line in *authoring* but produces regions as *output*. Two design
consequences noted now so v1 doesn't preclude them: (1) the data model should
allow a **feature to generate child features** (the same pattern as a building
owning generated sub-parts), and (2) the region geometry model (border polygon +
breaklines) must stay a clean subset a corridor generator can emit into. Not
built in v1; striping is a further corridor output.

## 4. Object model

An **object** is a discrete real-world thing (tree, sign, pole, hydrant, valve,
manhole, inlet…). Evidence is a cloud mass / points / DXF block / photo / manual
placement; objects are **excluded from the ground TIN** (their footprint is an
exclusion zone).

**Parametric objects (the owner's model).** Objects placed from a catalog stamp
all look alike until tuned per-instance. A **tree** template carries `height`,
`dripline` (canopy radius), `leafCoverage`, `trunkHeight`; a **light pole**
carries `height`, `armCount`; etc. The stamp defines the symbol/primitive and
its parameter schema; the instance stores values. This is what makes a placed
population read as real variation rather than clones. **(owner, 2026-07-09)**

**Answers to the required object questions:**

- *Minimum object creation UX?* Pick a template from the Add Object dropdown →
  cursor enters place mode → click in the viewer (snapped to evidence) → object
  drops at that coordinate with default parameters → tune parameters in the right
  panel. One click to place, done.
- *Start as placed point/symbol objects?* Yes. v1 objects are **point-anchored**
  (a coordinate + orientation) rendered as a symbolic primitive/billboard.
  Footprints/bboxes/meshes are later.
- *How does a cloud mass become evidence?* In v1, **manually**: the user places
  the object by snapping to the cloud, and the picked coordinate + nearby node
  reference are stored as `evidenceRefs`. Auto-fitting an object to a cloud
  cluster is deferred (needs the surfel/extraction work the owner wants to do
  first).
- *Geometry start: point, bbox, footprint, or primitive?* **Point + primitive.**
  The reality look is a scaled primitive/symbol driven by parameters; the CAD
  look is a block/point at the same coordinate.

## 5. Building model

A **building is its own family**, not an object subtype — it is a *composite*
feature (a footprint that owns generated sub-parts), which objects are not. This
is the one place a small hierarchy is justified.

**v1 building = footprint + roof (owner's chosen ambition), with an explicit
ramp** to doors, windows, garages, and decks. **(owner, 2026-07-09)**

```
Building (v1):
  geometry:
    footprint   closed polygon (snapped to evidence)
    height      eave/wall height (number)
  parameters:
    roofType    flat | gable | hip
    roofPitch   number (deg, ignored for flat)
    ridgeAxis   inferred from footprint or user-set
    overhang    number (plan offset distance)
  generated reality:
    wall mass (extruded footprint to height)
    roof planes (from roofType + pitch + ridge)
  generated PLAN/CAD output (the owner's priority):
    footprint line     (layer: BLDG-FOOTPRINT)
    wall/face lines    (layer: BLDG-FACE)
    overhang line      (footprint offset outward; layer: BLDG-OVERHANG)
    roof outline / ridge / hip lines (layer: BLDG-ROOF)
  surface behavior:
    footprint punched as an EXCLUSION ZONE in the ground TIN
  report:
    building note / review item; footprint area
```

**The ramp (post-v1), designed now so v1 doesn't box it out.** Buildings own an
optional list of **sub-features** attached to a face or roof plane:

```
Building.subFeatures[]:
  opening   window | door | garage   (on a face: uv-position + width + height)
  deck      (a footprint region attached at a Z)
  overhangDetail, dormer, roofPlane-edit, ...
```

In plan view, openings render as symbols/dashed lines on their own layers
(`BLDG-WINDOW`, `BLDG-DOOR`, `BLDG-GARAGE`) — exactly the building-survey
richness that ordinary land surveys omit. v1 ships the `subFeatures[]` array in
the schema **empty and inert** so the ramp is a data-model addition, not a
rewrite.

**Answers to the required building questions:**

- *Own type or object subtype?* **Own family** (composite with sub-features).
- *Minimum building feature?* Footprint polygon + height.
- *Footprint required?* Yes — it is the anchor and the exclusion zone.
- *Height required?* Yes in v1 (drives mass + roof). A footprint-only "mass TBD"
  state is allowed as a `draft` lifecycle but does not generate a roof.
- *Overhang?* A parameter (plan offset), generated as an offset line + roof
  eave. Not hand-drawn in v1.
- *Roof and faces deferred?* Roof is **in** v1 (flat/gable/hip generators).
  Editable individual faces and multi-plane custom roofs are deferred; v1 faces
  are generated, not independently editable.
- *Footprint → exclusion zone?* Automatically. Completing a building footprint
  registers an exclusion zone keyed to the building id, so the ground surface
  never absorbs the building.

## 6. Ground surface model

**Ground is the ground model, not the total reality model.** It is a **derived,
sim-level property** (not a feature tab), compiled from ground-level regions
and/or fed by an imported TIN asset, with **objects and buildings excluded**.
This matches the owner's current thinking: a surface that material/regions drape
onto, with structures punched out.

```
Ground Surface (sim-level, derived):
  inputs (ALL surface constraints, whoever owns them):
    - ground-level Region patches (borders as boundary constraints)
    - breaklines (region-owned OR standalone) — hard edges the surface must honor
    - spot-elevation markers — single XYZ control points the surface must pass through
    - imported TIN asset (LandXML/DWG surface), optional
    - exclusion zones (building/object footprints)
    - [later] cloud extraction
  outputs:
    - the visual sim ground (v1: rendered region patches)
    - [later] a stitched derived-surface asset
    - [later] DWG contours / breaklines on export
```

**Answers to the required ground questions:**

- *Feature, sim property, or generated asset?* **Sim-level derived property**,
  and *also* re-crystallizable into a derived **asset** on export. It is not a
  feature tab.
- *Imported TIN as an asset feeding ground?* Yes. An imported LandXML/DWG TIN is
  an ordinary asset; the sim uses it as a ground input via a sim layer. (v1 can
  display an imported TIN; *blending* imported TIN with region patches is a
  surface-manager phase.)
- *User-authored ground patches as features?* Yes — a ground-level region **is**
  the authored patch. There is no separate "ground patch" feature; regions serve
  that role.
- *Regions define ground patches?* Yes — that is the primary path.
- *Breaklines?* Internal linework added to a region after its border
  (centerline, ditch, grade break); shared region edges act as breaklines when
  stitching. Stored in v1; consumed by the later stitch engine.

**Surface constraints — the owner's ruling (2026-07-09).** Breaklines belong
*with* regions, not off in a separate world: a breakline is fundamentally a
**surface constraint** (a hard edge where grade changes), and a region must
recognize its own breaklines **and** any **spot-elevation markers** dropped
inside it, so the resulting surface is correct. Design consequence: breaklines
and spot elevations are a **shared constraint type** the ground compiler always
consumes, regardless of which tab created them. A breakline authored while
editing a region is *owned by* that region (its normal home); a breakline drawn
standalone still feeds the surface. A **spot-elevation marker** is a marker that
carries a measured Z and acts as a surface control point — the surface is forced
through it. The separate **Lines/breaklines tab** therefore exists only for
linework that is either (a) a *standalone* surface breakline not tied to one
region, or (b) *non-surface* linework (a fence line, an edge annotation). Nothing
about the tab lets a surface-affecting line escape the compiler.
- *Exclusion zones?* Building/object footprints punched as holes, keyed to the
  owning feature id.
- *Minimal first path?* **v1 renders region patches and stores breaklines +
  exclusion zones; it does not run a stitching/TIN engine.** The compiled TIN,
  region blending, and contour export are a dedicated **Surface Manager** phase
  (Risk 6 — do not build the TIN engine inside Create Sim).

## 7. Representation model

Features own **multiple parallel representations of one truth** — never separate
reality/DWG "twins." A single feature carries a reality view, a CAD view, a
report view, and an export mapping, all resolved from the same geometry +
parameters + template.

```
Feature.representations:
  reality:  { material?, primitive?, params-driven appearance }
  cad:      { layerRef, linetypeRef?, hatchRef?, blockRef?, pointCode? }
  report:   { label?, quantityKind?, note?, reviewStatus }
  export:   { enabled, targets[]?, mappingRef? }
```

**Design rule — resolve, don't duplicate.** The CAD representation stores
**references** (a layer name / hatch name / block name) that resolve through the
project **codelist/standards**, not baked geometry. Hatch fills, block
insertions, and contour lines are **generated at export time** from the authored
geometry + the resolved references. This is what prevents drift: there is one
geometry, and every view is a rendering of it (Risk 8).

**Answers to the required representation questions:**

- *What belongs in the feature now vs export-mapping later?* Now: the **reality
  params** and the **CAD reference keys** (layer/hatch/block/point-code) via the
  template. Later: the export *engine* that turns those keys into DWG entities.
  The feature holds the *intent*; the exporter holds the *mechanism*.
- *How much CAD metadata before the DWG manager?* Only the reference keys, seeded
  by the catalog/codelist. No linework geometry, no DXF group codes. Enough that
  a future DWG export is a lookup, not a redesign.
- *Report representation — placeholder only?* Mostly. v1 stores `reviewStatus`
  and a `label`/`note`; quantity rollups (area/count/volume) are computed later.
- *Preventing drift?* One geometry; representations are pure functions of
  geometry + params + resolved references; Sim/DWG is a **display-mode toggle
  over the same model**, never a second stored render (already the settled rule).

**6.5 The catalog / library (owner-confirmed).** A **catalog** of parametric
templates is the palette the Add tools draw from. Each template is a *type + a
parameter schema + default representation references*:

```
CatalogTemplate:
  id, family, subtype, displayName
  paramSchema:  { name, type, default, min?, max? }[]   # e.g. decay, verticalScale, height, dripline
  reality:      { primitive|material, param-bindings }
  cad:          { layer, hatch?, block?, linetype?, pointCode? }
  report:       { quantityKind?, defaultLabel? }
```

**v1 ships a short, trusted, built-in catalog as JSON** (Section 2 seed list),
wired into the Add dropdowns; per-instance parameters are edited in the right
panel. An **"Add to catalog" editor** (user-authored custom stamps) is designed
but **deferred** — the owner explicitly chose "trust a short list now, come back
to expand/enable Add." **(owner, 2026-07-09)** The catalog also feeds the
project codelist so exports come out standards-compliant.

**6.6 Catalog content sourcing (settled — owner, 2026-07-09).** Two different
things get sourced differently:

- *Definitions* (the JSON: type + param schema + layer/hatch/block names) are
  **hand-authored** — a dozen small entries, nothing to scrape.
- *Reality visuals* (how a tree/pole/asphalt actually renders) are **built as
  small procedural generators**, **not scraped**. This is deliberate: the model
  is parametric, and a downloaded static mesh/texture cannot honor `dripline`,
  `leafCoverage`, `height`, or `decay` — the parameters would go inert. Scraped
  game-asset libraries (Unreal/Sketchfab/etc.) also carry licensing risk, heavy
  files, inconsistent style, and a photoreal look wrong for a survey/CAD
  deliverable that wants symbolic clarity in top/ortho and clean export linework.
  What the owner admired in procedural-generation videos ("add tree, make it
  bigger/smaller, change canopy and leaf cover") **is** this approach — live
  parameters driving a generated primitive; we build our own lightweight version
  rather than porting an engine's library.
- *The one clean external source*: region **materials** may optionally layer
  **CC0 seamless textures** (ambientCG, Poly Haven — genuinely CC0) *under* the
  parametric params. Optional polish, not required for v1; v1 can start with flat
  tint + a param-driven pattern/shader.
- *CAD blocks and hatch patterns* need no sourcing now — v1 stores layer/hatch/
  block **names** only; actual blocks/hatches generate at export (a later
  manager), where standard public `.pat` pattern sets exist.

Consequence for scope: the implementer **builds reality-rendering components**
(procedural primitive + material generators). This is modest work (~10–40 lines
per template) and is scoped in the implementation plan, Section 4.

## 7b. Evidence / source-linking model

The first Create Sim implementation lets features reference source evidence
**without any automation** — the user's snap *is* the evidence link.

```
EvidenceRef (union, minimal → rich):
  kind: picked-coordinate            # ALWAYS present: the world XYZ the user clicked
      | asset-point                  # assetId + node/tile ref for a cloud point
      | asset-vertex | asset-edge    # DWG/LandXML linework snap
      | surface-hit                  # TIN/surface snap (later)
      | manual-note                  # free text, no geometry
  assetId?         # which asset the evidence came from
  assetLayerId?    # which hosted layer
  simulationLayerId?
  coordinate       # [x,y,z] in project CRS
  sourceClass?     # ASPRS class of the snapped point, if any
  sourceRGB?       # captured color/intensity, if any
```

**Answers to the required evidence questions:**

- *Minimum evidence ref?* A **picked coordinate** (world XYZ). Every authored
  vertex/placement stores at least this. That alone makes a feature traceable.
- *Store source coordinate on every feature?* Yes — the picked coordinate is
  mandatory; richer refs (asset id, node, class, RGB) are captured when the snap
  landed on a specific asset element.
- *Store picked source asset IDs?* Yes when the snap resolves to an asset
  (point cloud node, DWG vertex). Free-hand placement in empty space stores only
  the coordinate + `manual-note`.
- *Surfel-derived evidence allowed?* Allowed but **flagged**: a surfel is an
  *impression, not measured truth* (per vocabulary). Snapping to a surfel is
  legal for placement, but the evidence ref is marked `assisted`/low-confidence,
  never `source`. **Do not treat surfels as source truth** (Risk 3).
- *Disclose authored vs source-snapped?* Yes — the feature's `authorship` + per-
  vertex evidence `kind` drive a badge in the feature detail ("snapped to cloud"
  vs "free placement" vs "from DWG").

**Snap-to-any-asset (owner requirement).** The owner was explicit: when drawing a
line or placing an object it must snap to **any** asset data, not just the point
cloud. Today only the cloud is wired. The design mandates a **pluggable snap
target system** (Section 9): snap-to-point (cloud), snap-to-vertex/endpoint
(DWG/DXF), snap-to-surface (TIN, later), and **snap-to-feature-vertex/edge
(region-to-region)**. v1 delivers cloud-point snap, DWG vertex/endpoint snap,
**and region-to-region endpoint/edge snap**. **(owner, 2026-07-09)**

**Region-to-region snap (owner ruling, 2026-07-09).** When drawing a region
boundary, the cursor must snap to the endpoints/edges of *existing regions* so
adjacent boundaries **share vertices exactly**. This is not cosmetic: shared
edges are what make the compiled ground surface **watertight** (no gaps or
overlaps between abutting patches) and let a shared edge act as a breakline.
v1's snap system therefore treats authored feature geometry as a first-class snap
target, not only imported assets.

## 8. First Create Sim UX

**Interaction model (owner-confirmed).** Each family's **+Add** button in the
right Sim panel summons that family's **contextual tool set into the viewer tool
rail** (the mount already exists, top-right). The specific subtype is chosen from
a **dropdown selector** in that tool set (Add Region ▸ asphalt/concrete/grass),
or via generic-drop-then-classify in the right panel. **(owner, 2026-07-09)**

Per-family v1 tool sets:

- **Region:** template dropdown · Draw Border (click to add vertices, snap on) ·
  Add Breakline · Close/Complete · Cancel. On complete → region appears in the
  Regions tab; parameters (decay / verticalScale / color) editable in the detail.
- **Building:** template dropdown (flat/gable/hip) · Draw Footprint · set Height ·
  set Roof params · Complete. On complete → mass + roof + plan lines generate;
  exclusion zone registers.
- **Object:** template dropdown (vegetation/pole/hydrant/…) · Place (click,
  snap) · nudge. On place → object drops with defaults; scale params in detail.
- **Line/breakline:** template dropdown · Draw · snap · Close/Complete.
- **Marker:** template dropdown (flag/control point/generic) · Place. Bodyless.

**Answers to the required UX questions:**

- *Which tools first?* All five families get a **thin** tool set (owner: "they
  all get an authoring toolset"). Depth is limited per Section 2 — buildings stop
  at footprint+roof, objects at point+primitive, regions at border+breakline.
- *Point picking/snapping?* Cursor picks from any visible asset via the snap
  system; visible snap markers show what will be grabbed (cloud point / DWG
  vertex). Free placement when no snap target is near.
- *Appears in the Sim panel?* As a row in its family tab with count badges
  (already shelled); selecting a row opens the **feature detail** (name,
  authorship badge, confidence, parameters, evidence summary, delete/rename).
- *Appears in the viewer?* Reality representation renders live as authored;
  selection highlights; handles for editing vertices reuse the existing
  `editing.ts` picking math.
- *Edit/delete/rename?* In the feature detail and via direct vertex handles.
  Editing geometry/params flips `authorship` to `edited` and bumps `modifiedAt`.
- *Save/reopen?* Features persist in the manifest `features[]` array (schema
  extended per Section 9); reopening the project rehydrates and re-generates
  display geometry from stored primitives + params. No derived geometry is
  persisted — it regenerates, keeping the manifest small and drift-free.

**Undo/redo & cancel.** Each authoring session (border, footprint) supports
in-session vertex undo and a hard Cancel that discards the draft. Cross-feature
undo/redo is a v1.1 nicety, not a v1 blocker.

## 9. Required schema / viewer / UI changes

**Schema (manifest) — additive, staged.** The current feature enum
(`marker | polyline | measurement`) stays valid; v1 *widens* the feature schema
rather than breaking it:

- Add `family`, `templateId`, `subtype`, `authorship`, `confidence`,
  `lifecycleStatus`, `evidenceRefs[]`, `parameters`, `representations`,
  `display`, `metadata` to `featureSchema` (all optional/defaulted so existing
  `marker|polyline|measurement` records validate).

## 10. Risks / unresolved questions

Tracked against the handoff's risk list:

1. **Feature model too broad for v1** — mitigated by per-family depth caps
   (Section 2) and the empty-but-present ramp arrays (`subFeatures[]`).
2. **Confusing feature authorship with asset truth** — mitigated by the hard
   separation in Section 1; enforced by keeping `truthStatus` off features.
3. **Treating surfels as source truth** — mitigated: surfel snaps are
   `assisted`/low-confidence, never `source` (Section 7b).
4. **Automating extraction before authoring works** — out of scope by ruling;
   auto-extraction waits for the surfel work the owner wants first.
5. **Overdesigning DWG representation** — mitigated: CAD rep stores reference
   keys only; the export engine is a later manager.
6. **Overdesigning TIN extraction** — mitigated: ground v1 renders patches +
   stores constraints; the stitch/TIN engine is a **Surface Manager** phase.
7. **Surface accidentally including objects/buildings** — mitigated by automatic
   exclusion zones on building/object footprints.
8. **Region/texture/hatch vocabulary confusion** — mitigated: "region" is the
   settled term; hatch is a generated CAD *reference*, not stored on the region.
9. **Sim/DWG drifting twins** — mitigated: one geometry, display-mode toggle.
10. **Point classification tooling too early** — not required by v1; classes are
    captured *passively* as evidence (`sourceClass`), not edited.
11. **Underdefined evidence links** — mitigated: mandatory picked-coordinate +
    optional rich refs (Section 7b).
12. **UI that can't be built incrementally** — mitigated: v1 turns existing
    shells live family-by-family; each tool set ships independently.

**Open questions for the owner / next phase:**

- **Parameter → geometry fidelity for grass/decay:** how "real" should reality
  materials look in v1 (flat tint + hatch vs shader-driven patchiness/tall
  grass)? Recommend **simple first** (tint + a coarse displacement), richer
  shaders later. *Needs an owner taste call during v1.*
- **Roof inference:** auto-infer ridge axis from footprint, or always
  user-set? Recommend **infer with override**.
- **Imported-TIN-as-ground blending** vs region-compiled ground precedence —
  defer to Surface Manager.
- **Left-panel Sim tab** (surfacing exported sim/ground assets) — carried from
  the display phase hold list; decide in v1 or Surface Manager.
